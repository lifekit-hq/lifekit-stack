# Customizing skills

A workspace skill is a `SKILL.md` file (plus optional helpers) that OpenClaw discovers and routes intent to. In `lifekit-stack`, every skill is **parameterized**: no personal data baked in, all user-specific values read from a single user-context file the wizard generates.

This page walks through the convention.

## File layout per skill

```
skills/<skill-name>/
├── SKILL.md            # the prompt (Jinja2 template)
├── defaults.yaml       # sensible defaults so the skill works without user input
├── README.md           # what this skill does, what context it expects
└── (optional helpers)  # scripts, data files, etc.
```

## SKILL.md as a Jinja2 template

Use `{{ user.* }}` substitutions for any value that varies by user.

### Anti-pattern

```markdown
# Workout planner

You are helping Denys plan his weekly workouts. Denys goes to FlyeFit Phibsborough,
trains 4x/week, focuses on push/pull splits, and is currently bulking.
```

This bakes in personal data — name, gym, schedule, goal. It won't pass `PRIVATE.md` audit. It won't be useful for anyone else.

### Pattern

```markdown
# Workout planner

You are helping {{ user.name }} plan their weekly workouts.

Their context:
- Gym: {{ user.workout.gym | default("not specified") }}
- Schedule: {{ user.workout.schedule | default("3x/week") }}
- Goal: {{ user.workout.goal | default("general fitness") }}
- Training style preference: {{ user.workout.style | default("balanced") }}

Always respect their preferences. Suggest progressive overload. Track sessions
in `~/.life/journal/workouts/`.
```

The skill works for anyone. Users with no `workout` context get sensible defaults. Users with rich context get a personalized assistant.

## defaults.yaml

Defines what each placeholder should fall back to. Example:

```yaml
# skills/workout-claw/defaults.yaml
workout:
  gym: "not specified"
  schedule: "3x/week"
  goal: "general fitness"
  style: "balanced"
```

The wizard merges these defaults with user-provided values. The user only has to specify what differs.

## The user-context schema

The wizard writes one file: `/srv/life/user.yaml`. It looks like:

```yaml
# Generated by `lifekit init-stack` on 2026-05-16
identity:
  name: "Jane Doe"
  email: "jane@example.com"
  timezone: "Europe/Dublin"
  language: "en"

workout:
  gym: "PureGym Camden"
  schedule: "4x/week"
  goal: "strength"
  style: "5-3-1"

nutrition:
  constraints: ["dairy-free"]
  cuisine_preference: "mediterranean"

# ... etc for any skill that needs context
```

Every skill reads from this file. There is exactly one place to update a personal value, and every skill picks it up automatically.

## Adding a new skill

1. **Pick a name.** Kebab-case. Examples: `gym-buddy`, `book-tracker`, `expense-logger`.

2. **Create the directory:**

   ```bash
   mkdir -p skills/your-skill/
   ```

3. **Write `SKILL.md` as a Jinja2 template.** Reference `{{ user.* }}` for any user-specific value.

4. **Write `defaults.yaml`** with sensible defaults for every placeholder.

5. **Write `README.md`** explaining what the skill does and what user-context fields it expects.

6. **Audit against `PRIVATE.md`.** Run:

   ```bash
   gitleaks detect --source skills/your-skill/
   ```

7. **Test render:**

   ```bash
   python scripts/test-render-skill.py skills/your-skill/
   ```

   This renders the template with `defaults.yaml` and asserts no `{{ }}` remain — i.e., every placeholder has a default.

8. **Open a PR** with `feat(skills): add your-skill` as the commit subject.

## Skills that genuinely can't be templated

Some skills encode such specific personal context that templating them defeats the point. Examples might be a financial-advisor skill referencing your real brokerage accounts, or a relationships-tracking skill referencing specific people in your life.

**These don't go in this repo.** Keep them in your private `~/.openclaw/workspace/skills/` only. They'll work on your deployment; they won't be in the public template.

If you want a personal-skills overlay strategy (separate private repo that mounts alongside the public skills directory at deploy time), open an issue — happy to discuss the pattern but not in scope for v0.x.

## OpenClaw skill conventions

This template's parameterization layer sits on top of OpenClaw's own skill model. For the underlying primitives — how OpenClaw discovers, scopes, and routes skills — refer to [OpenClaw's docs](https://docs.openclaw.ai/).

Important from OpenClaw: **workspace skills are cached at gateway startup**. After installing or editing a skill, restart the gateway:

```bash
docker compose -p openclaw restart openclaw-gateway
```

The `lifekit init-stack` wizard handles this automatically.
